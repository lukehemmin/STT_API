# 01. 요구사항

## 1. 목표

1. 음성·영상 파일을 전사하는 **HTTP API**를 제공한다.
2. 같은 전사 결과를 **실시간(스트리밍)** 으로도, **일괄(batch)** 로도 받을 수 있다.
3. 두 방식이 **동시에, 같은 순간에** 처리되어도 성능 저하·간섭 없이 동작한다.
4. 엔진(모델/벤더)을 교체해도 API 계약이 바뀌지 않는다.

## 2. 비목표 (이번 범위 밖)

- 화자 분리(diarization), 감정 분석, 요약 — 인터페이스만 열어두고 v2 이후
- 실시간 **번역** — 전사 텍스트만 제공
- 웹 UI — API만 제공 (데모용 최소 페이지는 선택)
- 모델 학습/파인튜닝

## 3. 기능 요구사항

### 3.1 Batch

| ID | 요구사항 |
|---|---|
| B-1 | 파일 업로드(multipart 또는 presigned URL)와 URL 지정을 모두 지원 |
| B-2 | 제출 즉시 `202`와 `job_id` 반환, 상태 조회로 진행률(%) 확인 |
| B-3 | 완료 시 JSON(세그먼트 타임스탬프 포함), TXT, SRT, VTT로 결과 조회 |
| B-4 | 웹훅 콜백(서명 포함)과 SSE 구독을 모두 지원 |
| B-5 | 취소 가능. 취소 후에는 과금/자원 점유가 즉시 중단 |
| B-6 | `Idempotency-Key`로 중복 제출 방지 |
| B-7 | 실패 시 재시도 가능한 오류(`retryable`)와 불가능한 오류를 구분 |
| B-8 | 긴 파일은 내부적으로 분할 처리하되, 결과 타임스탬프는 원본 기준으로 연속 |

### 3.2 Streaming

| ID | 요구사항 |
|---|---|
| S-1 | WebSocket으로 오디오 프레임을 보내면 `partial`/`final` 이벤트를 즉시 수신 |
| S-2 | `partial`은 같은 `segment_id`에 대해 여러 번 갱신될 수 있고, `final`은 확정 |
| S-3 | 무음/잡음 구간에서 불필요한 이벤트를 만들지 않는다(VAD) |
| S-4 | 세션 최대 길이, 무입력 타임아웃, 최대 동시 세션 수를 서버가 제한 |
| S-5 | 클라이언트가 느리면 서버가 백프레셔를 걸고, 연결을 조용히 끊지 않는다(명시적 오류 또는 drop 통지) |
| S-6 | `flush`(즉시 확정 요청), `end`(정상 종료), `ping` 제어 메시지 지원 |
| S-7 | 연결이 끊겨도 이미 확정된 결과는 조회 가능(세션 결과 보존) |
| S-8 | (v2) `resume` — 마지막 수신 `seq` 이후부터 재개 |

### 3.3 공통

| ID | 요구사항 |
|---|---|
| C-1 | `language` 미지정 시 자동 감지, 지정 시 고정 |
| C-2 | 단어 단위 타임스탬프 옵션 |
| C-3 | 테넌트/API 키 단위 쿼터·레이트 리밋·동시성 제한 |
| C-4 | 모든 응답에 `request_id`, 오류는 기계 판독 가능한 `code` 포함 |
| C-5 | 전사 결과 이벤트 스트림은 재생(replay) 가능해야 한다 — 늦게 붙은 구독자도 전체 흐름을 볼 수 있어야 함 |
| C-6 | 같은 오디오를 배치와 스트리밍 양쪽에서 동시에 요청해도 결과가 일관됨 |

## 4. 비기능 요구사항

| 항목 | 목표 (초기값, 벤치마크로 조정) |
|---|---|
| 스트리밍 지연 | 첫 `partial` p95 ≤ 700 ms, `final` p95 ≤ 1.5 s (발화 종료 기준) |
| Batch 처리량 | GPU 1장 기준 RTF ≤ 0.15, 1시간 파일 ≤ 10분 |
| 동시성 | 스트리밍 100 세션 + 배치 50 잡을 동시에, 스트리밍 지연 저하 ≤ 20% |
| 가용성 | API 99.9%, 워커 장애 시 세션은 명시적 오류, 배치는 자동 재큐 |
| 확장성 | API는 무상태 수평 확장, 워커는 GPU 노드 추가로 선형 확장 |
| 보안 | API 키 인증, TLS, 오디오/결과 접근은 소유자 한정, 웹훅 HMAC |
| 프라이버시 | 원본 오디오 기본 7일, 결과 기본 30일 보관 후 삭제(설정 가능) |
| 관측성 | 요청/잡/세션 단위 트레이스, 큐 대기·RTF·에러율 메트릭 |

## 5. 사용자 시나리오

**A. 회의 녹음 일괄 전사**
파일 업로드 → `202 job_id` → 폴링(또는 웹훅) → 완료 후 SRT 다운로드.

**B. 라이브 자막**
WebSocket 연결 → 100 ms 프레임 전송 → `partial`로 자막 갱신 → 발화 종료 시 `final` → `end` → `done`.

**C. 긴 강의를 올리고 앞부분부터 보기**
Batch 제출 → 같은 잡의 SSE 구독 → 앞 세그먼트는 실시간처럼 표시, 끝나면 최종 JSON 저장.

**D. 동시 부하**
여러 사용자가 B를 쓰는 동안 A/C가 제출됨 → 스트리밍은 우선순위 큐로 지연 유지, 배치는 남는 GPU 용량 사용.

## 6. 수용 기준 (Definition of Done)

- [ ] Batch: 1시간 한국어 파일 → 세그먼트 타임스탬프가 원본과 ±200 ms 이내로 연속, SRT 파싱 가능
- [ ] Streaming: 5분 발화에서 `final` 텍스트가 Batch 결과와 문자 오류율(CER) 차이 5%p 이내
- [ ] 동시성: 스트리밍 100 + 배치 50 부하에서 오류율 < 0.1%, 스트리밍 p95 지연 목표 유지
- [ ] 취소/타임아웃/워커 강제 종료 시나리오에서 상태가 `completed`로 잘못 남지 않음
- [ ] 늦게 붙은 SSE 구독자가 이벤트 1번부터 `done`까지 순서대로 수신
- [ ] API 키 없음/쿼터 초과/잘못된 포맷에 대해 문서화된 코드로 응답

## 7. 가정

- 초기 언어: 한국어 + 영어(코드 스위칭 포함), 모델은 다국어 Whisper 계열
- 배포: 컨테이너, GPU 1종(NVIDIA T4/L4/A10급) 가정
- 클라이언트: 서버 간 연동 + 브라우저(WS). 브라우저는 16 kHz PCM을 직접 보내거나 서버에서 리샘플
- 인증: 정적 API 키(추후 OAuth/JWT 확장 가능)
